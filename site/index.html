Agents work in parallel. Nobody tests their changes together.

Every branch is green on its own. The combination is what breaks — and it’s the one thing no branch’s CI ever runs.

9%+

of textually clean merges fail to build or pass their tests.

79%

of agent-authored pull requests are open at the same time as another one in the same repository.

1 in 5

Same study · 747 replayed merges

Those are the conflicts Git can see. Both large 2026 studies of agent pull requests — AgenticFlict, across 142,652 PRs, and Xu et al. — counted only textual conflicts. The ones that merge cleanly and break anyway went unmeasured.

When a type check of the merged tree catches it too, Hairline still gets there first: it runs when the pull request opens, not at the head of a merge queue, and it names the branch that changed the contract and the branch that depends on it.

Git compares lines. Hairline compares contracts.

  1. Reads three revisions

    The merge base and both branches, straight from git objects. Your working tree and HEAD are never touched.

  2. Diffs what each branch promised

    Signatures, members, exports and the literal values a type admits — each branch against the merge base, not line by line.

  3. Flags where they meet

    A finding fires only when one branch changes a contract that code newly added on the other branch depends on.

Never runs your code

Parsing and type checking only. No installs, no build scripts, no eval.

Stays on your machine

No network calls and no telemetry. One runtime dependency: the TypeScript compiler.

Evidence, not verdicts

Every finding shows the code on both branches, the rule that fired, and why it’s rated as it is.

Quiet by default

Code that was already broken on its own stays in its own branch’s CI. Hairline only reports what the two branches do together.

Measured against the check you already run.

Every test fixture is a real git repository in which both branches type-check on their own. We run a merge-queue-style tsc --noEmit on the merged tree over the same fixtures.

Read this before the numbers.

We wrote these fixtures alongside the analyzers, so 100% on them is a statement about the fixtures, not about your codebase. The first run on real history — six merged pull-request pairs in zod — raised no false alarms. That’s encouraging, and far too small a sample to call a rate.

How we measure

Questions

Can’t find it here? The docs go deeper, including the threat model.

Doesn’t a merge queue already catch this?

Often, yes — we measured it. A type check of the merged tree catches 9 of our 13 conflicts. Hairline flags those earlier, when the pull request opens instead of at the head of the queue, and names the branch that changed the contract and the branch that depends on it. The other 4 are invisible to a type check: a consumer typed as a plain string, an untyped JavaScript caller, two branches rewriting the same contract, and a changed default argument.

Does it run my code or send it anywhere?

No. Hairline parses and type-checks; nothing is executed or installed. It makes no network calls, and it reads your repository from git objects, so your working tree and HEAD are never touched — that’s asserted in its own test suite.

Which languages does it support?

TypeScript and JavaScript today, through the TypeScript compiler. The engine talks to a language through a single adapter interface, so adding one means writing that adapter and its test fixtures — nothing else changes.

Can it tell when behaviour changed but the types didn’t?

Not in general, and it doesn’t pretend to. When a value changes under a new caller — a default argument, say — it reports a low-confidence risk and says plainly that it hasn’t proven anything.

How fast is it?

Seconds per branch pair: about 5 to 20 on a 500-file repository, most of it spent in the type checker. Real merges touch around 1% of files, so Hairline only extracts full contracts for the files the branches changed and the files that import them.

What happens when it can’t finish?

It says so. Exit code 3 means the analysis didn’t complete, and it’s deliberately different from 0 — a failure should never read as “nothing found.” Every report also states how much of the repository it actually saw.

Run it on the branches you’re about to merge.

Node 22.6+ and git 2.38+. Nothing else to configure.

$ git clone https://github.com/Arnavnemade1/Hairline hairline
$ cd hairline
$ npm install      # one runtime dependency: typescript
$ npm run build
# conflicts between branches that share a base
$ node bin/hairline.js analyze --repo ../your-repo \
    --base main --branches agent-a agent-b

# one finding in full, with the code from both branches
$ node bin/hairline.js explain 8a47418b --repo ../your-repo \
    --base main --branches agent-a agent-b

# machine-readable report
$ node bin/hairline.js analyze --repo ../your-repo \
    --base main --branches agent-a agent-b --json
name: hairline
on: pull_request

jobs:
  semantic-conflicts:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0            # the merge base needs history

      - uses: actions/setup-node@v4
        with:
          node-version: 24

      - name: Install Hairline
        run: |
          git clone --depth 1 https://github.com/Arnavnemade1/Hairline /tmp/hairline
          npm ci --prefix /tmp/hairline
          npm run build --prefix /tmp/hairline

      - name: Check against a concurrent branch
        run: >
          node /tmp/hairline/bin/hairline.js analyze
          --base origin/${{ github.base_ref }}
          --branches ${{ github.event.pull_request.head.sha }} origin/agent-b

Replace origin/agent-b with any branch this pull request might meet — another agent’s open PR, say. A finding exits 1 and fails the check. By default that means high- and medium-confidence findings; add --min-confidence high to block only on conflicts Hairline can decide from the code alone.
